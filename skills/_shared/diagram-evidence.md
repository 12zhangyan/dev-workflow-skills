# 图表与证据

仅在方案、代码地图或业务说明确实需要图表时读取。目标是回答读者的问题，保持主路径、关键分支与证据边界清楚；简单关系用文字或表格即可，不要求每类图都画。画之前先问：一段文字或三列表格能否讲清？能就不画。

| 读者的问题 | 合适的表示 |
|---|---|
| 由什么组成、边界在哪里 | 组件/架构图 |
| 谁按什么条件做下一步 | 业务流程图 |
| 调用先后、回调与等待 | 时序图 |
| 数据从哪里来、经过什么、写到哪里 | 数据流图 |
| 什么事件引起状态变化 | 状态图 |

行为本身决定含义时，先认出语义模式，再选图型；模式决定必须画出的元素，图型只决定版式：

| 后端语义模式 | 必须可见 | 首选图型 |
|---|---|---|
| 异步受理（MQ、任务表、回调） | 受理返回点与最终完成点分开，消费方和失败去向 | 时序图 |
| 重试 / 补偿 / 幂等 | 重试上限或退避、幂等键、补偿触发与终态 | 流程图或时序图 |
| 实体生命周期 | 全部终态、禁止转换、触发事件与守卫 | 状态图 |
| 权限 / 租户隔离 | 鉴权发生位置、拒绝路径、隔离键 | 流程图 |
| 扇入 / 队列 / 限流 | 并发来源、容量或阈值、溢出行为 | 数据流图 |
| 新旧结构对比 | 前后两图节点标识一致，变化集中列出 | 两张同构组件图 |

先确认节点、边、方向、触发条件和关键终点，再排版。实际调用、数据传递、消息投递与状态转换分别表达；异步受理不画成业务完成。关键连线能回到代码/契约/日志位置，未知连接显式标待确认或未展开，不用布局补全不存在的关系。方案中的拟议关系与当前实现分开。

## 删减与预算

最好的修改通常是删除：总是同时出现的两个节点合并，布局已能表达的关系不画线，颜色或形状已能表达的标签删除。单图默认不超过约 12 个节点、18 条边，时序图不超过约 8 个参与者、24 条消息；超出时拆成概览图加关键路径详图，详图沿用概览中的节点标识。强调样式最多用在 1–2 个关键节点上。

给图可理解的名称与简短图例；正文、图与测试口径使用一致的状态和术语，异常、重试或补偿只在证据存在且影响理解时加入。

常见失败：每个节点同样的框导致层级消失；连线无标签却有分支含义；一张图混合当前实现与拟议改动；把 Mermaid 自动布局当成已排查的调用关系；为“完整”画出不影响结论的日志、监控节点。

默认复用项目已有 Markdown/Mermaid 和看板能力。交互 HTML 只在用户需要且写入边界允许时生成；搜索、聚焦、上游/下游高亮只能遍历已确认的图边，不推断运行时影响。保留可编辑图源，不为画图自动安装外部服务或写看板。

交付时分开核对业务含义、语法/构建与实际渲染；没有渲染工具时明确仅检查源码，不声称浏览器或视觉验证通过。图可渲染不证明调用链、部署或业务结果真实。

写入后用 [doc-check.js](scripts/doc-check.js) 的 `mermaid <文件>` 做语法近似检查（Markdown 或看板 entry JSON 均可）：`error` 是图头未知、`subgraph`/`alt` 等块未闭合或标签含未加引号的括号，必须修正；`warn` 是超预算或反引号，按上文拆分或说明保留理由。该脚本只做静态启发式检查，通过不等于渲染成功。
