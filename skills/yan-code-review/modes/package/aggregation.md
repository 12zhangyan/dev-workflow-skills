# Yan Code Review Finding Aggregation

## 汇总规则

### 分级

| 等级 | 判定 |
|------|------|
| Critical | 已证实可触发严重数据损坏、重大安全影响或核心流程不可用，必须修 |
| Important | 可触发的行为错误、重要回归或契约失效，影响明确但未达到 Critical |
| Minor | 有证据的有限影响缺陷或验证缺口；纯命名、风格偏好不算 finding |
| Rejected | 误报、无证据、超范围、与项目规范冲突、收益低 |

### 去重与 ID 归并

同一文件/方法/根因的问题合并为一条，保留：
- 最明确的触发路径、证据和相关反证
- 由已证实影响支持的严重度，不自动取来源中的最高评级
- 最可执行的修复建议
- 所有 reviewer 的来源别名和原始编号

Finding ID 规则（保证发现→修复→关闭全链路追溯；前缀语义见 [../../../_shared/workflow-chain.md](../../../_shared/workflow-chain.md#finding-id)）：
- 首次聚合按最终严重度分配 `CR-n` / `IM-n` / `MI-n`，拒绝项标 `RJ-n`、阻塞项标 `BK-n`；保留 reviewer 的原始编号作为 source alias。
- 同一根因的后续结果复用 canonical ID；严重度变化记录历史，不静默换号。同根因但影响或修复边界不同的问题不机械合并。
- 修复交接和 `review-repair` 回填沿用 canonical ID，不得另起编号。

分歧按证据裁决，不以 reviewer 数量或最高评级代替判断。区分“后果有多严重”和“是否已证实能发生”；更高影响未证实但局部缺陷已证实时，保留已证实 finding，把额外影响列为待验证，不据此升级或撤销整条问题。

### 接受标准

Accepted finding 必须同时满足：
- 能定位到文件、方法、接口或数据路径
- 有可达的触发路径或违反明确契约的证据，不只是"可能"
- 能说明实际影响，并已检查会改变结论的调用方限制或防护

Accepted 只表示问题已证实，不表示已经具备修复条件。修复方式或验证设计未知时保留原 finding ID 和缺口，不因建议缺失归入 `RJ`；需要用户裁决时可关联 `BK`，但不得丢失原问题。

下发执行型修复前，协调者或 repair 必须依据代码、契约和授权补齐期望行为、修复边界与验证方式；无法补齐时将该 ID 的修复状态标为 blocked/deferred，仅继续独立项。

证据不足、误报或超范围时归入 `RJ`，注明是未证实、已被反证排除还是超范围；不能把未证实写成已排除。业务、权限、接口口径未决时归入 `BK`。`MI` 也必须满足以上证据标准。

### 结果有效期与覆盖

聚合前核对每份结果的范围与基线；基线至少能识别实际 diff/内容，只有 HEAD 相同不能证明未提交内容相同。修复或新改动影响的文件、调用方、契约和适用规则须重审；经核验仍相同且不受影响的单元可以复用，保留来源与 findings，不要求无差别全量重跑。不同版本的结果不能拼成一次完整通过。

送达、已读、已返回和已核验分开；只将完成取证且通过协调者核验的覆盖计入结果。失败、截断、缺失回复或未审单元保留为缺口，不作为零 findings 的成功投票。已返回结果仍可含有效 findings；覆盖不完整与缺陷是否存在分别判断。

### 材料不足

如果 review 结果指出关键证据缺失（例如没有 diff、没有关键源码、yan-dev-doc 与代码不匹配、状态/权限语义未确认），先归入 `OpenQuestions` 或 `blockers`，不要生成可直接执行的修复操作码。只有证据补齐或用户明确确认口径后，才能进入修复交接。
