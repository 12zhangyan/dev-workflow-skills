# Requirement analysis

## 目标

把用户在对话里陆续给出的口述、文档、图片、代码片段等零散需求，整理成开发者和后续 Agent 能直接使用的需求分析：解决谁的什么问题、改变哪些可观察行为、遵守哪些业务规则、哪些现有行为必须保持、如何验收，以及哪些问题仍需用户裁决。

本 Skill 只分析和澄清需求，不设计技术方案，不修改业务代码，不执行数据库写入，不自动 add、commit 或 push。默认产物为 `docs/requirements/<日期>/<需求>.md`；用户只要聊天输出时不落盘。不登记 HTML 看板。本 Skill 自包含运行，不依赖外部 Skill 或方法论。

## 完成标准

- 每个功能点有稳定编号 `REQ-n` 和优先级 `P1/P2/…`，写明角色/入口、前置条件、业务规则、正常结果和异常/边界结果；不适用的维度省略。`P1` 是能独立交付和验收的最小完整范围，可拆出的部分标后续优先级。
- 需求与现状分开：代码已证实的现有行为、需求要求的行为、两者差异，以及受影响的调用方、数据和权限。现有缺陷不自动成为需求，期望行为不冒充已经实现。
- 验收标准可观察、可判定；涉及权限、状态或副作用时，同时写明应发生的结果和必须保持的拒绝、隔离或不执行行为。
- 每条结论能追溯来源：用户口述（第几轮）、文档章节、图片、代码片段或仓库 `路径:行`。推断和假设单独标出。
- 待确认问题 `Q-n` 按对结果的影响排序，每个写明为什么影响结果、可选口径、Agent 推荐及依据；推荐不等于确认。
- 状态如实：`Draft`（尚未经用户确认）、`NeedsConfirmation`（仍有阻塞问题）、`Confirmed`（阻塞问题都已由用户裁决）。

## 读取输入

- 用户口述：记录原意，区分用户明确说的内容和 Agent 的理解。前后轮说法变化时以较新的明确说法为准，并记录变化；无法判断哪个有效时列为 `Q-n`。
- 文档：记录路径和章节。文档与口述冲突时两者都保留，列为 `Q-n`，不静默折中。
- 图片（原型、截图、流程图、表格）：只记录能看清的页面元素、字段、文案和流程。看不清或靠推测补全的部分标“图片推断”，不凭图片编造字段类型、接口、校验规则或数据口径。
- 代码片段：仓库中能找到对应位置时，以仓库当前版本核对并记录差异；找不到时标“用户提供片段，未与仓库核对”。
- 密码、token、连接串和敏感业务值只记录位置、类型和风险，不回显值。

## 对照现状

围绕需求涉及的入口、业务规则、状态/权限、数据归属和副作用，在仓库中定位现有实现，只读取足以判断差异和影响的代码、配置、契约或测试。不做全仓巡检，不展开技术设计。找不到相关实现时说明搜索依据，标为新增能力或待确认，不编造调用链。

记录基线时，Git 仓库读取当前分支和修订；SVN 工作副本只在 `detect-vcs` 返回的 SVN 根目录运行本地只读的 `svn info --non-interactive` 与不带参数的 `svnversion`，不运行联网或写入命令；命令不可用、报错，或出现 `svn: warning`、`Unversioned directory` 时基线写“SVN 未检查”。

## 澄清

需求澄清是本 Skill 的主要产出，但先用证据自答：能从材料或代码判断的直接采用并标来源；低风险未知写成有依据的假设和可修订边界。只把会改变业务结果、范围、权限、数据口径或验收的问题交给用户。

边聊边澄清时，每条回复依次包含：

1. 用几句话复述当前理解；首轮附上材料和代码中与之相关的已证实事实。
2. 只问一个当前影响最大的问题：为什么影响结果、可选口径、推荐及依据。
3. 可以按推荐处理的低风险项，合并成一份默认采纳清单，请用户一次确认或指出异议。

其余待确认问题留在分析的 `Q-n` 中，等后续回复再逐个提出。用户要求一次给出完整分析或全部问题时，按完整分析输出，问题集中列在 `Q-n`。用户回答后更新同一份分析，重新检查回答是否引出新问题或推翻已有结论。用户表示先到这里，或运行在无人值守环境时，保存当前内容为 `NeedsConfirmation`，不等待回复，也不替用户选择高风险口径。

证据冲突需要用户裁决、或目标文件存在冲突时，才读取 [交互策略](../_shared/interaction-policy.md)。

## 写入

准备输出完整分析时才读取 [需求分析模板](analysis-template.md)，按需求裁剪；小需求只保留影响结论和验收的部分。文档的读者是开发者和后续 Agent：每个事实只写一处，不复述项目已有的通用约定，篇幅以能直接据此设计和验收为限。

用 [workflow-fs.js](../_shared/scripts/workflow-fs.js) 创建日期目录并检查目标 `file-state`。同一需求的后续澄清轮次视为已授权更新：先读后改，保留已确认结论和任务外内容，记录本轮变化。默认名称冲突且用户未锁定路径时选稳定后缀，重新检查后写入并报告实际路径；目标不可读、状态未知，或精确路径冲突且未获修改授权时停止写入。

落盘后用 [doc-check.js](../_shared/scripts/doc-check.js) 的 `refs <分析文件>` 核对仓库路径和 `路径:行` 引用：`MISSING` 只能是已标为拟新增或外部的路径，`LINE_OUT_OF_RANGE` 必须改正。

准备标为 `Confirmed` 且宿主允许委派时，可派一个只读子 Agent 以实施方视角阅读分析，只返回它据此无法开工的问题。把这些问题分成三类：文档已有答案的补进正文，可自行决定的写成标注过的假设，需要用户裁决的列为 `Q-n`。不能委派时说明未做独立检验。

数据修复或结构变更类需求只记录期望的数据结果和核验口径；DDL/DML 只能作为待用户或 DBA 审批的建议。

只有真实跨 Agent、跨任务或稍后恢复时，才读取 [Workflow Brief](../_shared/workflow-brief.md) 并在分析文档中保留一份。

## 交付

报告分析状态、文档路径（或未写原因）、本轮已确认的结论和仍阻塞的 `Q-n`。给出下一动作：仍有接口、权限、状态、数据库或事务等技术决策待裁决时，建议以本文档为来源交给 `yan-dev-doc`；目标和验收已经清楚时可直接实施。不自动调用其他 Skill，不把需求确认说成方案已评审或已实现。
