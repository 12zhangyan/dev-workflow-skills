# Business document reference

只在准备生成持久业务文档或有证据边界的 `NeedsConfirmation` 草稿时读取。以下是可选信息结构，不是固定章节清单；不适用的节整节删除。

## 最小骨架

```markdown
# <业务名> 业务地图

> 状态：已证实 / 草稿待确认 ｜ 日期：<YYYY-MM-DD> ｜ 基线：<VCS 分支@修订>
> 范围：<已覆盖入口；缺失或排除的入口>

## 业务概述与可观察结果
[用测试/产品语言说明谁触发、要达成什么、成功或失败能看到什么]

## 流程与规则
[用最清楚的组合呈现：短文、决策表、业务流图、时序图或状态图；规则引用 E-n]

## 数据与副作用
[仅列与目标相关的表/字段、缓存、消息、外部调用和核对点；纯查询写“无持久化副作用”]
```

测试口径的“预期”只写当前已实现或已确认的业务期望；现有缺陷与期望冲突时在证据表标为冲突，不写成验收标准。

## 按需维度

- 多角色或多渠道：补角色、入口、权限和上下文差异。
- 有明确状态字段：补允许/禁止转换、终态和失败状态。
- 跨服务、异步或回调：补调用时序、重试、幂等和最终一致性观察点。
- 多数据对象：按阶段说明读写、关键字段变化和测试核对方式。
- 契约变化：说明请求、响应、错误行为或副作用对测试的影响。
- 后续要由 Agent 补自动化测试：在测试口径中标注已有测试位置或建议的测试层级（单元 / 集成 / 接口），不写未经验证的命令。

不要为完整感填空章节。每个结论应能回到证据或被明确标为假设。
