# Incident document reference

只在准备生成持久事故文档时读取。以下结构按证据与读者需要裁剪，不是固定流程；不适用的节整节删除。证据表是事实的唯一出处，其他节用 `E-n` 引用，不复述。

```markdown
# <故障标题> 事故记录

> 状态：草稿待确认 / 调查中 / 根因已证实 / 待验证 / 已关闭 ｜ 严重度：<仅影响当前优先级时填写>
> 日期：<YYYY-MM-DD> ｜ 发生版本/环境：<部署包、版本或环境> ｜ 分析基线：<VCS 分支@修订>

## 现象与影响
- 期望 / 实际：...
- 影响：<对象、时间范围、频率、绕行方式>
- 复现：<状态与触发条件>

## 时间线
| 时间 | 事件 | 证据 |
|---|---|---|

## 证据链
| ID | 证据（日志/请求/数据/代码/构建/部署位置） | 能证明 | 不能证明 |
|---|---|---|---|
| E-1 | | | |

## 根因
- 结论强度：已证实 / 高可能 / 候选假设（依据 E-n）
- 机制：<从触发到现象的因果链>
- 已排除：<解释及排除依据 E-n>
- 版本漂移 / 待确认：...

## 下一动作
<按下方三种状态之一书写>

## 验收证据
- 命令/操作与结果：...
- 尚未覆盖：...
```

时间线只在事故跨多个时间点（发布、首次出现、告警、止血、修复）时保留。

“下一动作”按当前状态选一种写法：

- **根因未证实**：列出能区分候选假设的最小诊断动作，写明命令/查询和各假设下的预期结果；不生成执行型 changeList/todos。
- **根因已证实、尚未修复**：写成执行 Agent 可直接开工的修复入口——修复位置（`路径:行` / `类.方法`，与根因机制对应）、修复边界与禁止改动、修复前应失败且修复后应通过的复现测试、回归风险与需同步检查的调用方，并附可复制提示：“请阅读 <本文档路径>，按‘下一动作’的边界修复，先确认复现测试在修复前失败，修复后回填‘验收证据’；根因或边界与现状不符时停止并报告差异。”
- **修复已实现（工作区或已合入，复盘）**：本节改名“修复方式与后续核验”，写修复位置、边界和已运行的验证，并写明修复所在的 VCS 状态（未提交 / 已提交 / 已合入）与部署状态；未合入或未部署时状态写“待验证”，不写成已修复上线。再列部署、数据影响等尚待核验的动作；不生成可复制修复提示。

严重度不机械套 P0-P3。修复建议必须与已证实机制相连。
