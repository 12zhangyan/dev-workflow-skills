# Incident document reference

只在准备生成持久事故文档时读取。以下结构按证据与读者需要裁剪，不是固定七节流程。

```markdown
# <故障标题> 事故记录

> 状态：NeedsConfirmation 草稿 / 调查中 / 根因已证实 / 等待验证 / 已关闭
> 发生范围与版本：...
> 关键证据：日志、请求、数据、代码、构建或部署位置

## 现象与影响
- 期望 / 实际：...
- 影响对象、时间范围、频率与绕行方式：...
- 复现状态与触发条件：...

## 证据链与根因状态
| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| ... | ... | ... |

- 已证实事实：...
- 根因或候选假设：...
- 已排除解释：...
- 版本漂移 / 待确认：...

## 下一动作
[根因未证实：能区分假设的最小诊断动作，写明命令/查询和各假设下的预期结果]
[根因已证实且未修复：写成执行 Agent 可直接开工的修复入口]
[修复已合入（复盘记录）：本节改名“修复方式与后续核验”，写已落地的修复位置、边界和提交/版本证据，再列部署、数据影响等尚待核验的动作；不生成可复制修复提示]
- 修复位置：<路径:行 / 类.方法，与证据链中的机制对应>
- 修复边界与禁止改动：...
- 复现测试：<修复前应失败、修复后应通过的测试或命令>
- 回归风险与需同步检查的调用方：...
- 可复制提示：请阅读 <本文档路径>，按“修复入口”的边界修复，先确认复现测试在修复前失败，修复后回填“验收证据”；根因或边界与现状不符时停止并报告差异。

## 验收证据
- 命令/操作与结果：...
- 尚未覆盖：...
```

严重度只在影响当前优先级时记录，不机械套 P0-P3。修复建议必须与已证实机制相连；根因未证实时不得生成执行型 changeList/todos。
