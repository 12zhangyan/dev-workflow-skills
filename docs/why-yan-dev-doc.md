# 为什么需要 yan-dev-doc

`yan-dev-doc` 不是所有开发任务的前置流程。它只在用户明确要方案，或接口、权限、状态、数据、事务、跨模块等关键决定尚未裁决时，把当前证据整理成可执行、可评审、可验收的开发方案。

需求、范围和验收已经清楚且用户要求直接实现时，Agent 应直接开发与验证，不为“走流程”额外生成文档。

## 它解决什么问题

复杂改造失败通常不是缺少固定模板，而是目标、现状、约束和验收没有落到同一份可复核证据上。`yan-dev-doc` 让 Agent：

- 从代码、契约、配置、日志、VCS 和用户材料中预填事实；
- 区分已证实内容、假设、已裁决冲突和真正 blocker；
- 按用户或系统可观察结果拆分工作，而不是按 Controller/Service/Mapper 或固定角色机械分层；
- 给出能证明目标行为的验证方式，同时说明未覆盖边界；
- 把数据库、秘密、文件覆盖、VCS 和外部副作用保留为明确授权边界。

## 表达深度由证据决定

| 模式 | 何时使用 | 核心产物 |
|---|---|---|
| `Compact` | 证据充分，风险与依赖能短篇说清 | 一份精简 md |
| `Standard` | 契约、数据、权限、状态、事务、跨模块、发布或回滚需要展开 | 一份完整但可裁剪的 md |
| `IncrementalRevision` | 已有可读方案，只需记录变化与继续有效的约束 | 一份增量 md |

模式不由代码行数、文件数、切点数或测试数量决定。Agent 可在证据扩大时调整表达深度，也可删除无关章节。

## 少打扰，保留自主空间

Agent 先从证据推断，只问会改变业务结果、权限、不可逆选择或方案成立性的 blocker；不设固定问题数量或提问轮次。高风险未知不必抹掉已完成分析：任务范围可识别时可以形成 `NeedsConfirmation` 草稿，但未知部分不能变成确定性实现指令、API/数据契约或数据库授权。

工作切片只固定目标、硬边界、真实依赖、完成判据和验证证据。执行 Agent 可自主合并、细分、重排或并行委派，普通文件布局、实现手段、工具和角色不需要逐项回到方案请示。

## 派生产物全部按需

- OpenAPI 只在新增接口或契约变化时生成。
- HTML 看板只在用户明确要求、已有交付档案需要续写或下游契约要求时发布。
- Workflow Brief 只在真实跨 Agent、跨任务或延期恢复时生成。
- 普通实现、测试、调试和验收由当前 Agent 自主完成，不依赖外部方法论 Skill。

这些产物不能冒充实现或运行证据：方案生成只证明方案已形成，实际完成仍需当前 diff、命令结果和目标行为验证。

## 自定义

- 修改触发、边界和执行原则：`skills/yan-dev-doc/SKILL.md`
- 修改方案表达、拆分和交付标准：`skills/yan-dev-doc/SKILL.md`
- 修改按需发布能力：`skills/yan-dev-doc/publishing-openapi.md`、`publishing-board.md`

保留目标、约束、授权和验收，其他组织方式交给 Agent；不要为了团队习惯重新加入固定问题数、固定章节、固定工作包或固定后续流水线。
