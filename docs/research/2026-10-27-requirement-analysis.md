# 2026-10-27：新增 yan-requirement-analysis 与参考实现对照评测

新增第 5 个公开入口 `yan-requirement-analysis`。这推翻了 [2026-10-20](2026-10-20-superpowers-adoption.md) 中“不引入第 5 个公开入口”的决定：用户明确要求一个独立的、对话式的需求分析入口，并保留 `yan-dev-doc` 可单独使用。

## 参考对象

| 来源 | 借鉴点 | 处理 |
|---|---|---|
| GitHub spec-kit `specify` / `clarify` / `checklist` | 一次一问并附推荐；歧义分类扫描；“需求的单元测试” | 一次一问采纳；分类扫描与质量自检因无基线失败未采纳 |
| obra/superpowers `brainstorming` | 复述理解后再提问；builder check（实施方视角试读） | 复述采纳；可实施性检验作为补能力空白落地，无基线 |
| spec-kit 用户故事优先级、AI-DLC 自适应深度 | P1 可独立交付 | 采纳为 `REQ-n` 优先级 |
| superpowers 硬门禁、Kiro EARS | — | 未采纳：与“门禁是证据状态”冲突；中文用“前提 → 操作 → 结果”更自然 |

## live 结果

条件：Claude Code 2.1.311，`claude-sonnet-5-5`，explicit 调用，fixture `scripts/fixtures/requirement-ticket-sla`，每组 3 次，独立隔离克隆。草稿版通过 `--skill-source` 运行已保存的草稿快照。prompt、grader、fixture 两侧一致；契约哈希不同只因中途放宽了 `accepted_routes`，路由标签按人工判读。机器可读摘要见 [results.json](2026-10-27-requirement-analysis-results.json)。

| case | 观察项 | 草稿版 | 修订版 |
|---|---|---:|---:|
| conversation-cadence | 首条回复只问 1 个问题 | 0/3（每次 7–8 个） | 3/3 |
| conversation-cadence | 复述理解 + 代码事实 + 默认采纳清单 | 0/3 | 3/3 |
| coverage-quality | `REQ-n` 带优先级，导出拆为 P2 | 0/3 | 3/3 |
| 两个 case | 埋点全部识别（部门隔离、工作时间冲突、转派、“快速”未量化、已删除工单） | 6/6 | 6/6 |
| 两个 case | 工作区零写入 | 6/6 | 6/6 |

- **规则准入依据：** 一次一问和优先级有基线失败，按“输出形状 → 正向配方 / 遗漏元素 → 模板栏位”落地。歧义覆盖表和需求质量自检的对照组已经全部识别埋点，按准入标准不加。
- **样本量小：** 每组 3 次，只能说明这两项从 0/3 变为 3/3，不代表稳定改善率；同版本噪声在 10-20 记录中曾达 40 个百分点。
- **仍需观察：** 修订版 run 3 把“转派后计时起点”放进了低风险默认清单，这一项可能被用来规避超时，风险不低。只此一例，暂不加规则。
- **环境：** 首轮 6 次全部被用户级 PreToolUse hook 拦截（找不到 Git Bash），结果作废；重跑时只给子进程设置 `CLAUDE_CODE_GIT_BASH_PATH`。
- 评测输出中的 ROUTE 标签五花八门（`chat-clarify`、`conversational-clarification` 等），无 mode 的入口不适合用路由标签自动判定。

## TypeMe 实测

条件同上，fixture 为 TypeMe `main@3789b11` 的干净克隆（原工作区未读写）。需求为口述：“成员管理页筛出今天 AI 次数已用完的成员，勾选多人批量改每日额度并马上生效，额度最好能一键恢复默认”。TypeMe 专用 case 只加在临时 worktree，未进入本仓库 evals。

| case | 次数 | 结果 |
|---|---:|---|
| 需求分析，边聊边澄清 | 2 | 2/2：每次 1 个问题（勾选范围），附推荐与默认采纳清单；代码事实带真实行号 |
| 需求分析，落盘（收紧前模板） | 2 | 2/2：文档 17.2k / 19.6k 字符，`refs` 32/32 |
| 需求分析，落盘（收紧后模板） | 2 | 2/2：文档 8.1k / 7.2k 字符，`refs` 36/36、25/25；5 个代码发现全部保留 |
| dev-doc 单独使用（无需求文档） | 2 | 2/2：正常出方案和看板，未提需求分析；两次对“额度为 0 是否算用完”自行做了相反的决定 |
| dev-doc 引用需求文档（Q-1、Q-2 已确认） | 2 | 2/2（人工判读；runner 判 1/2，因第 2 次 ROUTE 写成 `dev-doc`）：方案头部注明需求文档来源，采用已确认口径，Q-3~Q-6 原样列为待裁决、只阻塞批量切片，未重复提问。两次都发现 P2 的 REQ-3 在需求文档中没有 AC，自行补拟并建议回写。第 1 份按切片逐个引用 AC，第 2 份只写“沿用 AC-1～AC-9”，追溯粒度较粗。另有一次早先运行在第 2 次因宿主额度耗尽中断，不计入 |

- **P2 缺验收**：收紧模板时让验收只覆盖 P1，dev-doc 在用户确认 P2 后两次都只能自行补拟 REQ-3 的 AC。模板改为每个功能点都有验收（P2 一两条核心结果，依赖未决 Q 时注明）后，TypeMe 落盘 2/2：REQ-3 有 2–3 条 AC 并标注依赖 Q，篇幅 6.5k / 7.1k 字符，`refs` 16/16、27/27。其中 1 次把“最好有”的恢复默认标成了 P1（注明依赖 Q-1），与此前 4 次标 P2 不同。
- **文档过长**是这次真实会话里观察到的失败（用户反馈）：同一代码事实在功能点和现状对照各写一次，通用约定逐条重复。按“输出形状”类处理，在模板中写明每节内容；篇幅减半后信息未丢。功能点里仍偶有一两句通用约定。
- dev-doc 单独使用时两次口径相反，正是需求分析要显式交给用户裁决的那类问题。
- TypeMe 的 `project-html/` 未纳管，干净克隆中 `build.js` 会从空目录重写已纳管的 `docs/INDEX.md`。这是 TypeMe 的纳管问题，不是 skill 缺陷（该索引带生成标记，按设计可覆盖）。
