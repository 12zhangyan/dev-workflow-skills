# 按 yan-dev-doc 方案实现时的过度拆分与防护 需求分析

> 状态：Confirmed ｜ 日期：2026-10-29 ｜ 基线：Git main@599bc71（工作区另有与本需求无关的 mermaid vendor 删除） ｜ 澄清轮次：7 ｜ 来源：用户口述第 1~7 轮

## 背景与目标
用户观察到（第 5 轮）：先用 `yan-dev-doc` 写方案，再按方案开发时，Agent 经常做不必要的拆分、加不必要的防护代码。目标是让 `yan-dev-doc` 的方案不再把实现引向过度设计，并能用可复现的评估证明改动前后的差别。原则：没有完全安全的代码，只有合适的代码（第 3 轮）。

- 非目标：不精简本仓库自身的脚本和工具代码（第 4 轮）；不新增专门的“实现” skill；不削弱真实需要的鉴权、数据完整性和兼容要求（`skills/yan-dev-doc/SKILL.md:43` 已有，保持）。

## 功能点

### REQ-1 方案不诱导过度实现（P1）
- 规则：按方案实现的 Agent 只读方案文档，不读 `yan-dev-doc` 的写作规则；克制原则必须出现在方案里，让实现方看得到：新增类、接口、层次、校验、兜底、重试，须能追溯到某条验收 `A-n` 或证据 `E-n`，否则不加。
- 规则：方案中的拒绝/隔离要求、风险清单只写本任务真实适用的条目；不适用的不留空位，也不罗列。已有机制覆盖的风险注明“已由现有 xx 保障”，不让实现方再写一遍。
- 规则：工作切片是交付顺序，不是代码结构；方案不暗示一个切片对应一个类、文件或层。
- 结果：同一小需求按新方案实现，结果仍然正确，改动规模不大于按旧方案实现，人工判读没有无依据的拆分或防护。

### REQ-2 可复现的前后对比（P1）
- 规则：新增一个评估用例：在夹具项目上对一个小需求先用 `yan-dev-doc` 写方案，再按方案实现；用行为校验器判定实现是否正确。
- 规则：结果额外记录改动规模（新增/删除行数、新增文件数），比较时报告中位数差；结论以 diff 人工判读为准，改动规模只作参考。
- 规则：前后对比沿用现有的新旧 skill 版本比较（`--skill-source` + 比较器），不新增“无 skill”运行方式。
- 结果：旧版 skill 能复现过度设计时，REQ-1 才落地；复现不出来就不加规则（`CLAUDE.md` 编辑规则）。

### REQ-3 有/无 skill 对照（P2）
- 前几轮的有/无 skill 对照降为 P2，只在需要回答“skill 整体是否比不用更差”时再做。

## 验收标准
- AC-1（REQ-2）：用当前版本 skill 运行新用例 N 次 → 记录实现是否正确、改动规模和 diff；人工判读能指出至少一处无依据的拆分或防护，否则 REQ-1 不落地，并如实报告未复现。
- AC-2（REQ-1）：改动后的 skill 运行同一用例 N 次，与 AC-1 比较 → 实现正确率不下降，改动规模中位数不增加，人工判读中无依据的拆分或防护减少。
- AC-3（REQ-1，保持）：需求真的涉及鉴权、数据完整性或并发时，按新方案实现仍包含对应的必要防护；现有 dev-doc 评估用例和 `node scripts/check-all.js` 通过。

## 真实样本（TypeMe 仓库，第 6 轮用户授权用于测试）
- 样本 1：方案（外部仓库 TypeMe）docs/2026-10-28/成员AI额度筛选与批量调整-开发方案.md → 实现提交 `3ee07fe`。方案用“Agent 代决（错了的代价）”定下多条严格拒绝规则：重复 id 拒绝、恢复默认时携带数值拒绝、上限必须服务端强制（E-12、E-13），验收 A-7 又逐项列出。实现时同一组校验写了两层：控制器 Bean Validation 一层，服务层手写一层；前端还校验自家后端的响应结构。方案的验收表每行都有“必须保持”列。生产代码约 240 行，测试和验收脚本约 900 行。没有看到明显的过度拆分。
- 样本 2：方案（外部仓库 TypeMe）docs/2026-10-27/注册验证码与防刷方案.md → 实现提交 `73cf61a`。小站注册防刷落成 4 层限流、nonce 落库、清理任务、缺密钥失败关闭；被否决的方案用“误配到生产就是裸奔”的口吻排除。新增 4 个生产类，约 440 行。
- 结论：两个样本的多余部分以防护为主，拆分不明显，支持 H-1、H-2，以及新增的 H-5：“Agent 代决（错了的代价）”和否决理由的写法让方案作者偏向更严的防护，实现方照单全收并逐层加固。H-4 暂无证据，不改。

## 对照结果（第 7 轮，TypeMe 隔离克隆，每组各 1 次，Opus 5.5）
需求：成员列表接口按用户名关键字搜索，只做后端。实现方只读方案，看不到 skill；三组都能运行 Maven。

| 组 | 方案里 Agent 加的规则 | 生产代码 | 测试代码 | 结果 |
|---|---|---|---|---|
| 直接实现（无方案） | — | 约 95 行，改造现有方法加关键字参数 | 75 行 | `AdminApiIT` 14/14 通过 |
| 旧模板方案 → 实现 | 关键字须匹配 `[a-z0-9_]{1,32}`，否则直接返回空结果、不查库（作废的首次运行里，同一位置定为返回 400） | 约 83 行；多一层关键字正则拦截，新增 4 个与现有方法平行的查询方法 | 214 行 | `AdminApiIT` 21/21、`SecurityBoundaryIT` 9/9 通过；Agent 自己指出拦截会让不符合现行规则的历史用户名搜不到 |
| 新模板方案 → 实现 | 明确不做字符集或长度校验，搜不到就返回空列表 | 约 86 行，结构与直接实现基本一致 | 223 行 | `AdminApiIT` 21/21、`SecurityBoundaryIT` 9/9 通过 |

- 结论：旧模板两次写方案都给关键字加了需求外的校验，实现方照做；新模板的方案主动放弃这层校验，实现与直接实现一样克制。每组只有 1 次（旧模板写方案有 2 次），是回归样本，不是比率。
- 另一个现象：两组按方案实现的测试代码都约为直接实现的 3 倍，因为每条验收都写成了测试。用户没有把测试量列为问题，本轮不处理。
