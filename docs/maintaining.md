# Maintaining dev-workflow-skills

Developer reference moved out of `AGENTS.md` / `CLAUDE.md` so the agent guide only carries what every skill edit needs. User-facing installation, board usage and the check command list live in [README.md](../README.md); runtime behavior lives in each `SKILL.md` and `skills/_shared/`.

## Host eval runner

Cross-platform filesystem decisions use `skills/_shared/scripts/workflow-fs.js` instead of assuming Bash. Stable behavior contracts live in `skills/_shared/host-contracts.json` and are checked by `node scripts/check-portable-contracts.js`. This is an offline routing/side-effect contract suite, not evidence of live-model behavior. `node scripts/run-host-evals.js --preflight --host <host> --case <case> --workspace <git-worktree>` performs read-only filesystem/Git inspection without host calls, cloning, graders or network access. It checks configuration, skill resources, a clean committed fixture, declared `required_fixture_paths`, and output containment; runtime credentials, services and ignored dependencies remain unresolved. Live runs repeat these checks before probing the host; prepare dirty work in a separate fixture, never auto-commit or discard the original. `node scripts/run-host-evals.js --probe` reports real Claude Code, Cursor Agent, and Codex CLI availability without model calls. Opt-in sampled evaluation uses `--live --host <host> --case <case> --workspace <git-worktree>`; the runner creates a temporary Git clone, stages the current checkout's `skills/` in a Git-ignored in-clone snapshot for sandbox access, and never writes the supplied workspace. Claude runs disable the host `Skill` tool so a user-installed skill of the same name cannot replace the snapshot, set `DISABLE_AUTOUPDATER=1` so the host cannot reinstall itself mid-series, drop `CLAUDE_CODE_SUBAGENT_EFFORT` so an unrecorded user override cannot change delegated-reviewer effort, and allow only read-only shell commands (`git diff/status/show/log`, directory change, file reads) beyond `node`. Evaluation compares HEAD, semantic index entries, protected Git metadata, and file hashes including ignored files and the Skill snapshot. These are final-state checks, not an OS sandbox or proof of no transient/external writes. `--skill-source <skills-directory>` selects a saved full skill tree for old/new comparisons while retaining the current task and grader; runtime snapshots exclude eval answers and contract files. Results record skill, prompt, contract, grader and fixture fingerprints. Natural selection cases use `--invocation catalog` for metadata-driven choice or `--invocation native` for discovery from the isolated `.agents/skills` tree (currently Codex command-event evidence only); include the no-skill negative control. Pin `--model` and Codex `--effort` for comparisons; `node scripts/compare-host-evals.js <old.json> <new.json>` rejects mismatched or incomplete recorded conditions. A matched sample is regression evidence, not an improvement rate. `--reps N` (1–20) repeats a live case sequentially, each run in a fresh isolated clone, and writes one series result keeping every run; the comparator then reports per-side pass rates and median metric deltas, and rejects any series with an incomplete host run or mixed conditions instead of dropping runs. A declared outcome verifier executes trusted, fixture-specific behavioral checks in a child process against the produced implementation, across all host adapters; it is not a security sandbox or a general-purpose command hook. Minimal-loading cases require a `LOADED_RESOURCES` receipt, reject forbidden/cross-mode resources, cap resource count, and record duration/output/resource-count metrics. Write-capable cases additionally require `--allow-write`, enforce their declared scope, and can assert produced artifact content with Unicode paths. Assessments require a successful host process as well as model stdout and actual artifacts; positive/negative text signals still need semantic review. Results retain declared artifact hashes and bounded content (64 KiB per file, 256 KiB total), identifying omitted content explicitly. Host diagnostics are retained only as a bounded head/tail summary.

## HTML board internals

**Division of responsibilities**: the md files are AI-execution documents (precise paths, change lists, commands, evidence, and actionable todos for Codex/Cursor); board entries are independently authored human-readable solutions. Narrative fields (`background`, `solution`, `coreDesign`, `symptom`, `rootCause`, `fixPlan`, …) explain the why, flow, trade-offs, scope, and observable acceptance criteria to a colleague who did not participate. They are never excerpts of the md. Agent-only fields (`changeList`, `todos`, `stackTrace`, `codeLocation`) must stay out of board payloads.

The board is a multi-file static page; skills write its lightweight catalog and human-detail sidecars only through `board-add.js` (plus shell upgrades, see below):

```
project-html/
  index.html               ← shell (local mermaid vendor with CDN fallback)
  css/board.css            ← styles (light workspace: system fonts, green accents, responsive navigation)
  js/board.js              ← rendering; declares `const BOARD_VERSION = N` at top
  js/vendor/mermaid.min.js ← ~3MB local vendor for intranet use; copy via bash cp, never Read+Write
  build.js                 ← Node build script (no deps): hydrates catalog + detail, generates pages/ + docs/INDEX.md; legacy archive only on --archive-legacy
  board-add.js             ← deterministic splitter/writer; matches deliveryId/sourceDocPath/docPath, deep-merges lifecycle detail, filters Agent-only fields, backs up, and guards record count
  data/changes.js          ← lightweight catalog for home/search/filter (plus htmlChangelog)
  data/details/<id>.js     ← independently written human solution loaded only after selection
  pages/<slug>.html        ← GENERATED lightweight detail pages sharing board assets (gitignored here)
  exports/<slug>.html      ← GENERATED self-contained page only on explicit --standalone export (gitignored here)
```

Entry kinds: docs (delivery dossiers created or continued by `yan-dev-doc` by default once the current revision of its md plan is settled and written; the shell is initialized when `project-html/` is missing, and an explicit "no board" request skips it), `kind:"bug"` (from `bug-fix`), `kind:"reading"` (from `code-reading`), `kind:"biz"` (from `biz-flow`, tester-facing business flow with `bizFlow`/`dataFlow`/`sequence`/`stateMachine` mermaid fields plus optional `roles`/`context`/`dataChanges`/`validations`/`dataObjects` rich fields). A delivery dossier carries `deliveryId`, `currentGate`, compact review health, and a nested human-readable `delivery` detail with plan/review/verification evidence. Direct package/repair/loop calls update that dossier by default when `deliveryId` or the source plan `docPath` matches an existing catalog entry, and never create orphan review entries; check updates it only when lifecycle recording is explicit. Entries carry `service` / `module` (two-level grouping) and `docPath` (repo-relative path to the source md, rendered as a `../<docPath>` link). Optional `updatedAt`, `pinned`, and `lifecycle:"active|backlog|archived"` fields govern the workspace/backlog/archive views; old entries remain compatible as Plan-stage records. The `apis` field only records new or signature-changed endpoints and may include `operationId` plus optional interface-level `specPath`. When `yan-dev-doc` generates importable Apifox/OpenAPI YAML, entries also carry `apiSpecPath` (for example `docs/apifox/<date>/<task>.openapi.yaml`) and usually `apiIndexPath:"docs/apifox/INDEX.md` so the board can link the import file directly.

**`build.js` (run only after a skill actually writes or updates the board, invoked as `node project-html/build.js`)** does three things: (1) resolves every catalog `detailPath`, hydrates the human solution, and incrementally maintains `project-html/pages/<slug>.html` using shared assets; missing/mismatched details fail explicitly, and inlined page data escapes `<`, U+2028 and U+2029 so narrative text such as `</script>` cannot end the data script; (2) regenerates `docs/INDEX.md` from the lightweight catalog, but never overwrites an existing index it did not generate; (3) only with `--archive-legacy` (and when `docs/archive/` is absent) copies scattered legacy docs into `docs/archive/`, so auto-initialized boards never scan the project by default. A self-contained page is generated only by `node project-html/build.js --standalone <docPath|slug>`. `slugOf()` and collision maps in build.js/board.js must stay identical.

Board writes go through **`board-add.js`** (`node project-html/board-add.js <entry.json>`). It deterministically splits one independently authored human entry into a whitelisted catalog and `data/details/<detailId>.js`, filters Agent-only fields, matches by `deliveryId`, `sourceDocPath`, then `docPath`, deep-merges lifecycle detail, updates event arrays idempotently by stable `eventId`, preserves governance state, maintains `updatedAt`, backs up `changes.js`, and aborts on parse/count regressions. Publishing and migration share an exclusive board lock; a competing writer fails with `BOARD_WRITE_LOCKED` and must retry after the holder finishes; a lock whose holder process on the same host exited, or any lock older than 10 minutes, reports `BOARD_WRITE_LOCK_STALE`, and only `--unlock-stale` (which rechecks staleness) may remove it. Review writes set top-level `"requireExisting": true`, so an unmatched or non-delivery target fails with `BOARD_TARGET_NOT_FOUND` instead of appending an orphan record. When a later write omits `summary`, the catalog summary is re-derived from the merged detail rather than the newest partial entry. Detail identities/paths are validated, linked write targets are rejected, and each catalog/detail file is replaced atomically. Before writing, `node project-html/board-add.js --check-migration` reports whether the catalog needs conversion. If it reports `BOARD_DATA_MIGRATION_REQUIRED`, run `node project-html/board-add.js --migrate` and recheck before writing; migration converts legacy rich entries without reading md. The template catalog ships empty.

Shell upgrades: when the project shell is older than the template, skills sync it to the template version before publishing (shell files only, never `data/`, never a downgrade), then run the migration check. They keep the old shell when its files have uncommitted local edits or the user declines the upgrade, and then inspect writer/reader compatibility instead; unknown compatibility blocks board publishing without discarding the main plan. Confirm command support before using migration flags on an old shell. **Bump `BOARD_VERSION` whenever shell behavior changes** (board.js, build.js, board-add.js, index.html, or css). Skills must run `node project-html/board-add.js` to write, then `node project-html/build.js`.

Two copies must stay in sync: `project-html/` and `skills/yan-dev-doc/assets/board/`. Shell files are byte-identical; template `data/changes.js` is empty and template `data/details/.gitkeep` only reserves the directory. Real detail sidecars are versioned project data; generated `pages/`, `exports/`, and repo-demo `docs/INDEX.md` remain ignored. Run `node scripts/check-board-sync.js` after shell changes.
